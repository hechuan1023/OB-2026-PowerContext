# sample-app 需求规格

本文件是「人读」的版本；机器可读版本在 `context.json`。
两者必须一起演进——`scripts/build_sample_context.py` 会用这里的结论去生成指纹基线。

## SPEC-001 订单总价与折扣的计算规则（v2，生效中）

- 生效日期：2026-03-01
- 作用范围：`app/pricing.py`、`app/order.py`
- 冲突主题：`pricing-rule`

规则：

1. 所有金额以「分」为最小单位的整数表示，禁止使用浮点金额。
2. 订单商品小计达到 10000 分（100 元）才可享受折扣。
3. 折扣在**服务端**按订单维度计算一次，不做逐行商品折扣。
4. 折扣后金额四舍五入到分。

## SPEC-002 支付超时与重试策略（v1，已失效）

> 本条已被 **SPEC-003** 取代，**禁止再按本条实现**。

- 作用范围：`app/payment.py`

规则：支付调用固定超时 3 秒，失败后固定重试 3 次。

被取代的原因：固定重试在网关抖动时会放大压力。

## SPEC-003 支付超时与重试策略（v2，生效中）

- 生效日期：2026-06-20
- 作用范围：`app/payment.py`
- 冲突主题：`payment-retry`
- 取代：SPEC-002

规则：

1. 单次支付调用超时默认 3 秒，可按调用方配置。
2. 失败后最多重试 3 次，重试间隔 200ms。
3. 金额非法时**不重试**，直接失败。

## SPEC-004 支付超时与重试策略（v1 遗留副本，未标记失效）

> 这一条是团队在 SPEC-002 被取代时**忘了同步删掉**的旧版本。
> 它自己仍然写着 `active`，但版本号比 SPEC-003 老。
> 上下文模块必须发现「同一个主题有两条都声称生效的要求」，并按版本裁决，
> 而不是把两条一起丢给模型让模型自己猜。

- 作用范围：`app/payment.py`
- 冲突主题：`payment-retry`
- 版本：1（低于 SPEC-003 的版本 2）

## SPEC-005 订单总价与折扣的计算规则（v1 遗留副本，未标记失效）

> 同 SPEC-004，这是没清理干净的旧版本。
> v1 规定的是「折扣后金额向下取整到分」，v2（SPEC-001）改成了四舍五入。
> 两条同时生效会让 AI 助手写出两种取整方式。

- 作用范围：`app/pricing.py`、`app/order.py`
- 冲突主题：`pricing-rule`
- 版本：1（低于 SPEC-001 的版本 2）

## SPEC-101 订单明细按小计筛选（生效中）

- 需求：订单明细支持按商品小计筛选——`Order.expensive_items(min_subtotal_cents)`
  返回小计不低于阈值的明细，按小计降序；同小计保持输入顺序；
  阈值 `<= 0` 视为 0（返回全部明细，同样降序）。
- 小计 = 数量 × 单价（分）。不改变订单总价与折扣的任何规则（SPEC-001）。
- 作用范围：`app/order.py`
